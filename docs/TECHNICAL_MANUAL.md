# QQ 校园墙机器人技术手册

> 适用于本目录的 `main.py`。源代码来自本次提供的单文件附件，功能比旧工作区项目更完整；历史 `CHANGELOG.txt` 记录的是旧阶段，包含真实 QQ 号、路径和图片描述，**故未复制进开源目录**。本手册描述代码可确认的行为，不承诺 QQ 平台或外部 SDK 始终可用。

## 1. 工作原理

```
NapCat / OneBot v11 --反向 WS--> FastAPI /onebot/v11/ws
  ├─ 好友请求 → 校验策略 → 同意/拒绝 → 欢迎语
  └─ 私聊消息 → 权限命令分流 / 会话收集 → 空闲定时器
         → 图片预算与内容检查 → DeepSeek 文字+图片审核
         → Pillow 渲染截图 → QZonePublisher 上传图片、发布说说
         → SQLite 记录状态 / data 目录归档 / 向投稿人发送回执
```

- `create_app` 创建 FastAPI 应用，lifespan 初始化数据库、HTTP 客户端、OneBot 连接管理器、空间发布器、投稿管理器，关闭时释放资源。
- `ConnectionManager` 和 `OneBotConnection` 使用 OneBot 的 `echo` 匹配请求/回执；接收循环使用异步任务分发事件，避免阻塞 WS。
- `SubmissionManager` 按 QQ 号聚合私聊消息，空闲后启动投稿流水线。它同时处理急停、角色、额度、封禁、管理员命令与审核日志。
- `render_screenshot` 下载头像/图片素材并在线程中运行 Pillow；`_compose_screenshot` 决定卡片排版。背景/徽标属于可选装饰，读取失败不影响业务。
- `QZonePublisher` 用 `qzone-sdk==1.0.1` 的认证/传输接口，但自行组装上传与发布参数；这里依赖 SDK 内部接口，升级前应独立联调。
- `Database` 管理 SQLite `submissions`（内容、状态、展示编号、空间 tid）与 `blacklist`（封禁/拉黑）；旧表按需迁移。`data/roles.json` 保存运行时角色变更，暂停状态有独立文件。

## 2. 安装与启动

1. 准备 Python 3.10+ 和可运行的 NapCat（OneBot v11）；独立测试 QQ 号，勿在真实用户账号上先试。
2. `python -m venv .venv`，激活虚拟环境，执行 `python -m pip install -r requirements.txt`。
3. 复制 `.env.example` 为 `.env`；填入 `DEEPSEEK_API_KEY`、`OWNER_QQ`。`OWNER_QQ` 留空时**没有所有者**可以通过聊天命令任命/撤销角色。不要填写示例 QQ、旧值或真实密钥到公开仓库。
4. 确认 `QZONE_AUTH_MODE=napcat`、`QZONE_WS_URL=ws://127.0.0.1:3001` 与你的 NapCat 实际 WS 地址匹配；在 NapCat 侧配置反向 WS 到本服务的 `/onebot/v11/ws`。二者方向不同：一个供空间 SDK 使用，一个供消息接入。
5. 本机运行 `python main.py`；生产环境可运行 `python -m uvicorn main:app --host 127.0.0.1 --port 8080`，跨机时使用仅限可信网段的监听、认证网关或防火墙策略；本服务的 WS 路径**不含内建令牌验证**，切勿直接对公网暴露。
6. 请求 `/healthz`，然后用测试账号尝试好友请求、文字投稿、带图投稿、匿名投稿、`/帮助`、删除已发说说。核对审核结果、发布 tid、审核记录和截图。不建议只凭 `/healthz` 判断空间接口可用。

只读取与 `main.py` 同目录的 `.env`，不读取父目录其他项目的配置。`.env` 非空配置值优先于进程环境变量，空的 `.env` 值不会覆盖已有非空环境变量。改配置后重启，并查看启动日志中的配置来源与已脱敏密钥信息。部分运行时角色由 `data/roles.json` 提供；在部署前备份这个文件。

## 3. 配置要点

| 配置项 | 用途与注意事项 |
| --- | --- |
| `DEEPSEEK_API_KEY`, `DEEPSEEK_BASE_URL`, `DEEPSEEK_MODEL`, `DEEPSEEK_VISION_MODEL` | 外部审核服务；不要记录或提交真实密钥。模型兼容性需现场验证。 |
| `OWNER_QQ`, `ADMIN_WHITELIST`, `REVIEWER_WHITELIST` | 所有者、管理员、审核员；旧环境变量 `SUPER_ADMIN_WHITELIST` 有兼容行为，迁移时逐一确认权限。 |
| `SUPPORT_CONTACT_QQ` | 自定义好友欢迎语里的联系 QQ，默认留空。 |
| `HOST`, `PORT`, `WS_PATH`, `QZONE_WS_URL`, `QZONE_AUTH_MODE` | 服务监听、反向 WS 接入、空间认证。 |
| `QZONE_COOKIE`, `QZONE_UIN` | 手工 Cookie 模式才需要；存于本地密钥管理/`.env`，不可入库。 |
| `DATA_DIR`, `DB_PATH` | 本地归档和 SQLite 路径；应做权限控制与备份。 |
| `DAILY_MESSAGE_LIMIT`, `IDLE_TIMEOUT_SECONDS` | 每人每日计数、会话空闲收稿秒数，重启可能影响内存状态。 |
| `MODERATION_MAX_IMAGES`, `MAX_STICKERS_PER_SUBMISSION` | 每篇照片与表情额度；公开图片应在审核覆盖范围内。 |
| `MAX_SUBMISSION_IMAGE_BYTES`, `MAX_QUEUE_IMAGE_BYTES`, `MAX_IMAGE_PIXELS` | 单篇、缓存总量、解码像素的资源上限。 |
| `CHAT_BACKGROUND_PATH`, `ADMIN_BADGE_PATH`, `ADMIN_BADGE_ENABLED` | 可选本地图片。默认**不附带素材、不开启徽标**。仅引用你有使用权限的素材。 |
| `FACE_MAP_PATH` | 可选自行准备的 QQ 表情 JSON 映射，不随仓库分发。格式如 `{"14":{"cdn_id":"100","name":"微笑"}}`。未设置时不能保证 QQ 表情显示为图片，优先展示消息自带表情名称，否则退回 ID 文本。 |
| `FONT_PATH`, `DISPLAY_TIMEZONE` | 自定义授权字体与投稿显示时区；可安装系统允许使用的字体，勿提交无授权字体文件。 |
| `ALLOW_PRIVATE_IMAGE_HOSTS` | NapCat 本地图片可能需要为 true；若图片 URL 不应访问内网，应设 false 并测试来源。代码逐跳检查重定向，但网络隔离仍重要。 |
| `PURGE_BEFORE` | **危险**：可能删除数据库有 tid 的旧空间投稿；保持空值，除非备份并明确授权执行清理。 |

原附件中的部分旧设置/说明保留了兼容逻辑；`.env.example` 是本次公开副本的**安全起点**，不是原部署环境的镜像。

## 4. 投稿、审核与错误处理

- 按用户独立合并私聊消息。命令须先满足角色白名单与命令前缀，再按动作鉴权；非白名单的命令不会当作投稿发布。投稿人可用匿名关键词触发公开截图匿名，数据库里的 QQ 号仍保留，须在隐私政策中明确告知。
- 投稿图片经过类型判断、体积与像素限制、格式整理，再提交多模态审核。凡会进入公开截图/原图的内容，应纳入审核范围；无法覆盖时拒绝整篇发布，而不是放过未审图片。
- 审核请求报错/返回格式异常按单篇 fail-closed 处理；自动审核存在误报和漏报，组织应设置人工申诉、删除/封禁复核渠道，并自行审查审核提示词是否合法合规。
- `fetch_bytes` 流式取图且限制响应字节数；关闭私网地址访问时逐跳检查重定向。仅软件校验不足以代替部署级网络隔离与外网带宽限制。
- 截图背景默认为白色；自行配置背景时按图片比例缩放，正文过长则退回白底。自定义徽标仅作为装饰，默认关掉。
- 成功发布时写入空间 tid；删除命令依赖该 tid。发布失败、审核拒绝与图片错误应查看 SQLite 状态、归档及运行日志，勿把回执当作平台最终可见性证明。

## 5. 角色与命令

- 所有者：`OWNER_QQ`，管理员全部能力，另外可以设置/取消管理员和审核员；不应将 owner 设置为公共 QQ。
- 管理员：急停、恢复、状态、删帖、封禁/解封、查作者、拉黑、额度重置、审计查看等；投稿免于每日配额。徽标功能默认关闭，即使是管理员投稿也不会显示专属图片。
- 审核员：删帖、封禁/解封、帮助；删帖与封禁要求理由，解封范围受原封禁操作者限制。不同角色的 `/帮助` 输出不同，**以运行时实际输出为准**。
- 管理员命令示例：`/停止账号活动`、`/恢复账号活动`、`/状态`、`/删帖 <编号> <理由>`、`/封禁 <QQ号> [天数] <理由>`、`/解封 <QQ号>`、`/查作者 <编号>`、`/设置管理员 <QQ号>`。高权限操作应保留审计，尤其匿名作者查询与永久拉黑。

## 6. 数据、安全与运维

- `data/` 中可能含原始聊天内容、图片、投稿人 QQ、投稿截图、审核决策、角色名单。发布前扫描 **Git 全部提交历史**；`.gitignore` 只防新添加，不会删除已提交机密。如真实密钥曾入库，立即在供应商处轮换。
- 避免直接上传原附件 `CHANGELOG.txt`、旧 README、数据库、`run.log`、归档、默认图片和旧 `.env`；旧项目目录另有历史版本，不属于本目录交付。
- `HOST=0.0.0.0` 会扩大监听面，公网部署至少使用反向代理认证、网络 ACL、速率限制与 HTTPS/WSS。请遵守 QQ/NapCat/审核服务的使用条款，并取得投稿用户对数据处理的告知与授权。
- 日志包含投稿行为与管理操作，不要把日志当公开调试信息；根据当地法规和实际用途设置备份、留存、删除与数据泄露响应流程。
- 部署升级前备份 SQLite 数据库与 `data/roles.json`；切换版本前检查数据库迁移兼容性，先在测试环境执行。待发布队列与部分会话存在内存里，重启或急停会影响正在等待的投稿。
- 调试路径：健康检查 → WS 连接数 → NapCat 收发回执 → 审核 API 结果 → 图片下载日志 → 空间上传/发布响应 → 数据库状态/tid。勿将完整带令牌的图片 URL 或 Cookie 写进问题报告。

## 7. 测试与扩展

安装开发依赖后运行 `python -m pytest -q`；`tests/test_open_source.py` 覆盖无默认识别信息、徽标默认关闭、白底、可选素材等。代码级/离线测试通过并不等于外部服务联调完成。维护者修改审核、图片额度、角色鉴权或删除逻辑时，应增加 fail-closed、安全边界与旧数据库迁移的回归用例。

## 8. 发布与许可决策

- 个人项目、希望广泛复用且接受他人闭源改造：推荐 **MIT**。保留版权及许可证声明；在根目录添加正式 `LICENSE`，替换为真实版权人及年份。当前没有 `LICENSE` 是刻意的：版权归属必须由你确认。
- 希望显式专利授权/专利终止条款：可选 Apache-2.0，合规义务相应更细。若明确希望衍生作品开放源代码，再对比 GPLv3（这与宽松许可目标不同）。
- 先核实代码是否为你独立创作、是否有学校/团队职务作品、共同作者或外包协议；核实第三方 SDK、字体、图片、映射数据和平台内容是否可发布。不要把依赖包和平台素材的许可误认为你的项目许可。
- 发布前清单：人工查看全部文件和 `git status`；运行文本/大文件/密钥扫描；确定代码授权和投稿者隐私策略；补齐 `LICENSE`；再建**新的** GitHub 仓库，仅添加本目录，不要推送旧仓库历史。
